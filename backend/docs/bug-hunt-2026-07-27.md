## BUG-1. HIGH — Race Condition Double-Rotation pada `AuthService.Refresh` (Session Failure) — ✅ FIXED 27 Jul 2026

- **Severity:** High
- **Bug:** `Refresh()` menjalankan `FindSessionByJTI` → cek `RevokedAt` → `FindActiveSessionByJTI` → `RevokeSessionByJTI` → `issueSession` tanpa transaksi/locking. Dua request refresh bersamaan dengan refresh token SAMA (dua tab auto-refresh, retry klien) sama-sama membaca `RevokedAt=nil` sebelum salah satu commit, keduanya lolos validasi, keduanya membuat sesi token baru. Sesi pertama jadi token "liar". Saat token lama dipakai lagi, reuse-detection salah mengira pencurian → `RevokeAllActiveSessionsByUser` → user ter-logout paksa dari semua perangkat (false positive).
- **Reproduksi:**
  1. Login di 2 tab; access token (15 mnt) kedaluwarsa hampir bersamaan.
  2. Kedua tab menembak `POST /api/v1/auth/refresh` dengan cookie sama dalam milidetik berdekatan.
  3. Keduanya lolos `RevokedAt==nil`; dua pasangan token dibuat.
  4. Request berikutnya dengan token pertama → reuse detected → revoke-all → logout global.
- **Affected Files:** `backend/internal/services/auth_service.go` (`Refresh`), `backend/internal/repositories/auth_sessions.go` (`RevokeSessionByJTI`)
- **Recommendation:** Rotasi atomik dalam satu transaksi: `UPDATE auth_sessions SET revoked_at=now() WHERE token_jti=? AND revoked_at IS NULL` lalu periksa `RowsAffected==1`. Bila 0 → sudah dirotasi request paralel (jangan revoke-all); bedakan dari reuse jahat. Alternatif: `SELECT ... FOR UPDATE`.
- **Complexity:** Medium
- **Fix (27 Jul 2026):** Tambah repo method `RotateSession(jti) (bool, error)` — single atomic `UPDATE auth_sessions SET revoked_at=now() WHERE token_jti=? AND revoked_at IS NULL AND expires_at > now()`, returns `RowsAffected==1`. `AuthService.Refresh` kini memanggil `RotateSession` di awal: hanya pemenang race (`rotated=true`) yang menerbitkan token baru; pecundang race (`rotated=false`) ditolak TANPA `RevokeAllActiveSessionsByUser`. Untuk membedakan race sah dari theft sesungguhnya, `Refresh` membaca ulang `RevokedAt`: bila revokasi terjadi dalam window `refreshRotationConcurrentWindow` (1 menit) → race sah (concurrent refresh), log `EventRefreshFailed`; bila lebih tua dari window → tetap reuse/theft → `RevokeAllActiveSessionsByUser` + `EventRefreshTokenReuseDetected` (perlindungan theft dipertahankan). Cek `FindActiveSessionByJTI` yang redundant dihapus. Verifikasi: `go build ./...` + `go vet` + `gofmt` bersih.

## BUG-2. HIGH — Panic: Event Bus `Unsubscribe` Close Channel vs `Publish` Send (Data Race → Panic)   FIXED 27 Jul 2026

- **Severity:** High
- **Bug:** `events.Bus.Unsubscribe` memanggil `close(ch)` di bawah `b.mu.Lock()`, tetapi `Publish` mengirim ke channel di bawah `b.mu.RLock()`. Race window: `Publish` sudah melewati `for ch := range b.clients` dan mengeksekusi `ch <- event` tepat saat goroutine lain `Unsubscribe` menutup channel yang sama. Mengirim ke closed channel → **panic: send on closed channel**. Terpicu saat SSE client disconnect (defer Unsubscribe) berbarengan dengan event publish (booking/AI) — kondisi umum di production. Panic ini terjadi di goroutine publisher (bukan handler SSE), tidak ter-catch `Recovery()` bila publish dari goroutine lain.
- **Reproduksi:**
  1. Buka koneksi `GET /events/stream` (staff).
  2. Picu banyak event (chat AI / booking) sambil menutup koneksi SSE berulang kali.
  3. `Unsubscribe` menutup channel tepat saat `Publish` mengirim → panic.
- **Affected Files:** `backend/internal/events/bus.go` (`Unsubscribe`, `Publish`), pemicu `backend/internal/handlers/handlers.go` (`EventStream`)
- **Recommendation:** Jangan `close(ch)` di `Unsubscribe`; cukup hapus dari map (GC membersihkan setelah handler selesai). Atau kirim lewat mekanisme yang recover-safe. Paling aman: `Unsubscribe` hanya `delete(b.clients, ch)` dan biarkan `EventStream` berhenti via `c.Request.Context().Done()`.
- **Complexity:** Low
- **Fix (27 Jul 2026):** `Unsubscribe` tidak lagi memanggil `close(ch)` — hanya `delete(b.clients, ch)` di bawah `Lock()`. Setelah channel dihapus dari map, `Publish` tidak lagi mengirim ke channel itu, sehingga send-ke-channel-tertutup mustahil. `EventStream` berhenti via `c.Request.Context().Done()` (tidak bergantung pada channel close); sisa event di-buffer di-GC bersama channel. Komentar penjelas ditambahkan di `bus.go`. Verifikasi: `go build ./...` + `go vet` + `gofmt` bersih + test ad-hoc `go test -race` (Publish vs Unsubscribe paralel) tanpa panic/data-race.

## BUG-3. MEDIUM — Resource Leak: HTTP Body `triggerN8N` Tidak Ditutup

- **Severity:** Medium
- **Bug:** `payment_service.go` `triggerN8N`: `_, _ = client.Do(req)` — response body tidak dibaca dan tidak `Close()`. Transport HTTP tidak bisa reuse koneksi keep-alive; setiap trigger menggantung satu koneksi sampai GC/timeout. Pada volume webhook tinggi → file descriptor / koneksi menumpuk.
- **Reproduksi:**
  1. Set `N8N_WEBHOOK`, aktifkan payments.
  2. Kirim banyak webhook `paid` berturut-turut.
  3. Amati koneksi TCP ke host N8N menumpuk (ESTABLISHED/CLOSE_WAIT) dan FD naik.
- **Affected Files:** `backend/internal/services/payment_service.go` (`triggerN8N`)
- **Recommendation:** `res, err := client.Do(req); if err == nil { io.Copy(io.Discard, io.LimitReader(res.Body, 512)); res.Body.Close() }`. Idealnya panggil di goroutine dengan context timeout agar tidak memblok webhook response.
- **Complexity:** Low

## BUG-4. MEDIUM — Context Leak / Request Menggantung: SSE `WriteTimeout=0` + Tidak Ada Max Connection Lifetime — ✅ FIXED 28 Jul 2026

- **Severity:** Medium
- **Bug:** `main.go` `WriteTimeout: 0` dinonaktifkan global demi SSE (sudah dicatat ARCH-3 sebagai desain). Yang BARU: `EventStream` hanya keluar saat client disconnect atau heartbeat. Bila koneksi setengah-putus (client hilang tanpa FIN — NAT timeout, laptop sleep), `c.Request.Context().Done()` tidak terpicu cepat dan `<-time.After(25s)` terus membangunkan loop selama write masih "berhasil" ke buffer TCP. Tanpa TCP keepalive/timeout aplikasi, goroutine SSE bisa hidup sangat lama → akumulasi goroutine + subscriber bus bocor pada banyak koneksi zombie. (SEC-31 menangani timer leak; ini berbeda: lifetime koneksi zombie.)
- **Reproduksi:**
  1. Buka banyak koneksi SSE dari klien.
  2. Putus jaringan klien secara paksa (cabut kabel / kill -9 tanpa close).
  3. Goroutine `EventStream` tetap ada selama OS belum mengirim RST; subscriber di bus tidak berkurang.
- **Affected Files:** `backend/cmd/server/main.go` (http.Server), `backend/internal/handlers/handlers.go` (`EventStream`)
- **Recommendation:** Tambahkan write-deadline per-tulis di SSE (deteksi write error → return false), dan/atau batasi umur maksimal koneksi SSE + jumlah subscriber. Saat scaling, pisahkan server SSE (lihat ARCH-3).
- **Complexity:** Medium
- **Fix (28 Jul 2026):** Tiga lapis pertahanan ditambahkan ke `EventStream` + `events.Bus`, tanpa mengubah `WriteTimeout=0` (SSE tetap long-lived): (1) **write-error detection per-tulis** — `http.NewResponseController(c.Writer)` + `rc.SetWriteDeadline(now+10s)` sebelum `c.SSEvent` + `rc.Flush()`; error pada koneksi setengah-putus (buffer TCP penuh / RST) membuat handler return → goroutine keluar + subscriber dilepas. (2) **max lifetime koneksi** — `time.NewTimer(sseMaxLifetime=30 menit)`; saat umur tercapai, handler mengirim event `reconnect` lalu return; `EventSource` browser reconnect otomatis. (3) **cap subscriber** — `events.Bus.Subscribe()` kini `(chan Event, bool)`, menolak registrasi bila `len(clients) >= MaxSubscribers (100)`; `EventStream` membalas `503 Too many SSE connections` bila penuh, mencegah map `clients` tumbuh tak terbatas. Bonus: `time.After(25s)` (SEC-31 timer leak) diganti `time.NewTicker(sseHeartbeatInterval)` + `defer ticker.Stop()`. Verifikasi: `go build ./...` + `go vet` + `gofmt` bersih. Diff hanya `handlers.go` (`EventStream`) + `events/bus.go` (`Subscribe`/`MaxSubscribers`).

## BUG-5. MEDIUM — Error Ditelan: `AIService.Chat` Silent-Fail `FindChatSession` → Logic Bypass Rekomendasi — ✅ FIXED 28 Jul 2026

- **Severity:** Medium
- **Bug:** `ai_service.go` baris 112: `chatSession, _ := s.repo.FindChatSession(sessionID)` mengabaikan error. Bila query gagal sesaat (DB flake / pool habis) — BUKAN panic — `chatSession` zero-struct → `selectedTripID=nil`. Guard "paket sudah dipilih" (baris 128) dilewati, sehingga `showRecommendations` bisa true dan rekomendasi baru terkirim padahal user sudah memilih paket. Fail-open, bukan fail-closed.
- **Reproduksi:**
  1. `select_package` berhasil (SelectedTripID ter-set).
  2. Chat lagi; buat `FindChatSession` kedua gagal (putus koneksi DB sesaat).
  3. Response mengembalikan rekomendasi baru — workflow tidak konsisten.
- **Affected Files:** `backend/internal/services/ai_service.go` (`Chat()`)
- **Recommendation:** Tangani error: bila gagal fetch, anggap state tidak berubah dan set `showRecommendations=false` (fail-closed) atau kembalikan error 500. Jangan telan `_`.
- **Complexity:** Low
- **Fix (28 Jul 2026):** `Chat()` kini menangani error re-fetch sesi secara eksplisit. Bila `FindChatSession` kedua gagal, service meng-log peristiwa (`[ai] failed to re-fetch chat session ... suppressing recommendations (fail-closed)`), menandai `sessionStateUnknown=true`, dan **menekan seluruh rekomendasi** (`showRecommendations=false`, `recommendationReason=""`, `recommendedPackages=nil`) karena state terpilih tidak bisa diverifikasi. Respons teks AI tetap dikirim ke user (tidak 500) agar UX tidak putus. Guard "paket sudah dipilih" tidak lagi bisa di-bypass oleh kegagalan DB sesaat. Komentar penjelas BUG-5 ditambahkan di `ai_service.go`. Verifikasi: `go build ./...` + `go vet ./...` + `gofmt` bersih.

## BUG-6. MEDIUM — Race: Guest Session Dihapus Cleanup Saat Request In-Flight (Booking/Chat Gagal Intermiten)

- **Severity:** Medium
- **Bug:** `Chat()` memvalidasi `session.ExpiresAt` di awal, lalu menjalankan LLM + tool loop yang bisa berlangsung hingga 35 dtk. Ticker `CleanupExpiredChatSessions` (tiap jam) menghapus session + child-nya saat `expires_at < now`. Bila session tepat melewati expiry selama tool loop berjalan, cleanup bisa menghapus session di tengah proses; `AddChatMessage` assistant akhir atau `UpdateChatSessionSelectedTrip` bisa gagal/terhapus → respons sukses tapi data hilang, atau error intermiten yang sulit direproduksi.
- **Reproduksi:**
  1. Buat guest session dengan `expires_at` hampir habis.
  2. Kirim chat yang memicu tool loop panjang.
  3. Saat ticker berjalan di tengah proses, session terhapus; penulisan pesan assistant/error muncul acak.
- **Affected Files:** `backend/internal/services/ai_service.go` (`Chat`), `backend/internal/repositories/repositories.go` (`DeleteExpiredChatSessions`), `backend/cmd/server/main.go` (ticker)
- **Recommendation:** Perpanjang `expires_at` (sliding) SEBELUM tool loop (sudah dilakukan baris 67, tapi gap tetap ada bila proses > TTL) atau tandai session "in-flight" dan skip cleanup untuk session yang sedang aktif. Minimal dokumentasikan TTL harus jauh lebih besar dari `AITimeout`.
- **Complexity:** Medium

## BUG-7. MEDIUM — Integer Overflow / Float Precision: `total` Booking pada Harga & Pax Ekstrem

- **Severity:** Medium
- **Bug:** `BookingService.Create`: `total := tripAdultPrice(trip)*float64(adultPax) + tripChildPrice(trip)*float64(childPax)`. Meski pax dibatasi ≤20 (SEC-11), harga katalog (`BasePrice`/`DiscountPrice`/`EstimatedPrice`) adalah `float64` dari DB tanpa validasi batas atas saat input trip. Admin dapat mengisi harga sangat besar (mis. 1e15) via backoffice; `1e15 * 20` melampaui presisi aman float64 untuk sen dan tetap tersimpan ke `numeric(14,2)` yang bisa overflow/error DB atau kehilangan presisi. Tidak ada guard rentang harga di `TripRequest` (tidak ada binding `gte=0,lte=...`).
- **Reproduksi:**
  1. Buat trip dengan `base_price` sangat besar atau negatif (backoffice tidak memvalidasi tanda/batas).
  2. Buat booking; total bisa negatif/overflow presisi atau gagal insert ke `numeric(14,2)`.
- **Affected Files:** `backend/internal/services/booking_service.go` (`Create`), `backend/internal/dto/dto.go` (`TripRequest` tanpa validasi harga), `backend/internal/services/trip_service.go` (`buildTripFromRequest`)
- **Recommendation:** Validasi harga trip non-negatif dan ≤ batas wajar (mis. `lte=999999999999`) di DTO + service. Pertimbangkan integer sen untuk kalkulasi (lihat #13). Tolak harga negatif.
- **Complexity:** Low-Medium

## BUG-8. LOW — Error Handling: `GuestUser` Mengabaikan Error `bcrypt.GenerateFromPassword`

- **Severity:** Low
- **Bug:** `auth_service.go` `GuestUser()`: `hash, _ := bcrypt.GenerateFromPassword(...)`. Bila gagal (sangat jarang), `user.Password` kosong dan user guest tersimpan tanpa hash valid. Tidak berdampak login (guest tidak login), tapi menyimpan baris user dengan password kosong — inkonsistensi data; pola `_` ini berbahaya bila disalin ke jalur lain.
- **Reproduksi:** Sulit dipicu langsung (butuh kegagalan bcrypt); lebih sebagai latent defect.
- **Affected Files:** `backend/internal/services/auth_service.go` (`GuestUser`)
- **Recommendation:** Tangani error: `hash, err := bcrypt.GenerateFromPassword(...); if err != nil { return models.User{}, err }`.
- **Complexity:** Low

## BUG-9. LOW — Empty/Invalid Input: `parseDate` Mengembalikan `nil` Diam-diam untuk `travel_date` Tidak Valid

- **Severity:** Low
- **Bug:** `BookingService.Create` memakai `parseDate(req.TravelDate)` yang mengembalikan `nil` bila format bukan RFC3339/`2006-01-02`. Booking dari tool MCP `create_booking` mengirim `travel_date` dari teks LLM (mis. "12 Agustus 2026", "2026/08/12") yang sering gagal parse → `TravelDate=nil` tanpa error. Booking tersimpan tanpa tanggal perjalanan → admin tidak tahu jadwal; LLM mungkin mengklaim tanggal tercatat padahal kosong. Data validity issue pada jalur AI (booking failure tersembunyi).
- **Reproduksi:**
  1. Lewat chat, berikan tanggal dalam format natural ("besok", "12/08/2026").
  2. `create_booking` sukses (contact terpenuhi) tapi `travel_date` NULL di DB.
- **Affected Files:** `backend/internal/services/helpers.go` (`parseDate`), `backend/internal/services/booking_service.go` (`Create`), `backend/internal/services/mcp_service.go` (`executeCreateBooking`)
- **Recommendation:** Validasi/normalisasi `travel_date` di `executeCreateBooking` (minta format ISO ke LLM atau parse lebih banyak layout) dan/atau kembalikan error tool bila tanggal wajib tapi gagal parse. Pertimbangkan field wajib vs opsional eksplisit.
- **Complexity:** Low-Medium

## BUG-10. LOW — Concurrent Request: `ChatSessions` / `GuestHistory` Update Activity Non-Atomik + Lost Update `MemorySummary`

- **Severity:** Low
- **Bug:** Dua operasi pada session yang sama berpacu: `Chat()` memperbarui `MemorySummary` lewat `UpdateChatSession(&session)` (GORM `Save` menulis semua kolom — overlap DB-2) sementara `UpdateChatSessionActivity`/`UpdateChatSessionSelectedTrip` memakai `Updates` kolom tertentu. Pada concurrent chat cepat, `Save` dari `refreshMemorySummary` (yang membaca session lama di baris 415) bisa menimpa `selected_trip_id`/`last_activity_at` yang baru saja diubah tool → lost update pada session state.
- **Reproduksi:**
  1. Jalankan dua chat paralel pada session sama (atau chat + select_package cepat).
  2. `refreshMemorySummary` menyimpan struct session lama; field yang diupdate query lain tertimpa.
- **Affected Files:** `backend/internal/services/ai_service.go` (`refreshMemorySummary`), `backend/internal/repositories/repositories.go` (`UpdateChatSession` via `Save`)
- **Recommendation:** Update hanya kolom `memory_summary` (`Updates(map)` atau `Select("memory_summary")`) alih-alih `Save` seluruh struct.
- **Complexity:** Low
